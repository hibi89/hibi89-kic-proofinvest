# KIC DAKER frozen-PDF local upload eligibility guard — 2026-10-25 KST

## Issue and evidence
- Existing scripts/kic_submission_preflight.py validates byte size, %PDF- header, and pinned SHA-256 only. A byte-identical frozen PDF renamed with a final .txt or .pdf.txt suffix would return READY_FOR_USER_REVIEW_NOT_SUBMITTED even though the authenticated DAKER proposal upload screen displayed PDF-only files with a max size of 20MB. This is an offline preflight misclassification, not a server upload event.
- The user's authenticated screenshot showed logged-in team leader label, empty project title/file input, PDF-only upload box and max20MB; actual final submission authority and receipt remain unverified.

## Alternatives and implementation
- Chosen: check final filename extension case-insensitively for .pdf and conservatively reject files over decimal 20,000,000 bytes BEFORE content hashing. Existing pinned byte-identity rules continue to apply. Reject with PDF_EXTENSION_REQUIRED or DAKER_PDF_SIZE_LIMIT_EXCEEDED. No path/file content logged, copied, uploaded, parsed or modified; no third-party dependencies.
- Not chosen: relying on header and SHA only, which permits correct PDF bytes with an upload-invalid .txt filename; or creating a renamed copy of private PDF, which requires unnecessary private file mutation; or DAKER backend upload for a test, which requires separate user authorization.
- Restrict file extension after ordinary-file and no-symlink checks, preserving existing missing/directory error behavior. Uppercase .PDF is allowed.
- Conservative decimal 20MB limit chosen because the screenshot does not establish whether the site's 20MB means decimal MB or MiB; the frozen 513,113-byte PDF is comfortably below either. A local pass never proves the DAKER backend will accept the PDF.
